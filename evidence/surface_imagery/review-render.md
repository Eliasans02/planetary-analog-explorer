# Independent surface-imagery render review

Reviewed 2026-11-14 by the imagery-loader/terrain-analysis agent, who did not author the viewport integration. Read-only scope: `SurfaceViewport.tsx`, `surfaceUv.ts`, `latestResource.ts`, their focused test sources, both parent viewport call sites, and the installed Three.js basic-material/color-space paths. No render implementation changes or redundant suite reruns were made.

**Result: no material findings in the current integrated call paths.**

- Photographic rendering uses a white `MeshBasicMaterial`, `vertexColors:false`, and `toneMapped:false`. It does not multiply the imagery by the relief elevation colors or the synthetic lights. The installed Three.js program selector uses no tone mapping when material tone mapping is false, despite the renderer's ACES setting used for relief. The texture is declared sRGB and output is sRGB, providing the expected decode/encode path rather than applying the relief tone curve. This preserves the source appearance within ordinary texture filtering, framebuffer precision and display color-management limits; it is not a numerical screen-pixel equality claim.
- UV coordinates address native pixel centers: `(col+0.5)/width`, `(row+0.5)/height`. The image loader decodes with `imageOrientation:'none'`, and the texture uses `flipY:false`. Native rows therefore increase with texture v and native Z; row zero remains the row-zero edge of the surface. The asymmetric 2×2 fixture and non-square test source cover the intended four-corner orientation and denominators. No second vertical inversion was found.
- Scene creation depends only on `surface`, `heights` and `validMask`. Appearance selection has a separate request callback. Successful layer swaps change only the material/map and invalidate rendering; camera, orbit target, walking position, terrain geometry and native height sampling are untouched. Both current parents key the viewport by `surface.id`, so changing sites destroys old appearance state rather than applying another site's record to the new surface.
- The UI distinguishes requested selection from the actually displayed layer. Loading keeps the prior material visible, and the status text/source link come from `imageState.displayed`. A failed replacement preserves the prior displayed resource and reports an error with retry; it does not claim that the failed layer is visible. Manifest errors explicitly identify unavailability, while the default surface is labeled relief/elevation tint. Earth explicitly uses relief.
- `latestResource` aborts superseded requests and uses a revision guard before display. It releases late successful decodes, ignores stale errors, and releases the prior displayed resource only after a replacement has been installed. Resource release disposes the Three.js texture and closes its bitmap. Teardown marks the scene disposed, removes the image callback, aborts pending work, releases the current resource, then disposes materials/geometry/renderer. The loader also closes a bitmap if cancellation arrives during decoding. Ownership is consistent, with no double-close or wrong-current-bitmap release found along the ordinary completion, cancellation or failed-decode paths.
- Imagery integration does not change keyboard/mouse navigation handlers, walk step calculations, pause/resume, camera eye height or source-triangle bounds. The wireframe action updates both material variants. Switching appearance can blur the walking canvas through the existing focus/pause behavior; the camera position remains intact.

Boundaries: this review inspects implementation and focused test definitions; it does not assert GPU screenshot parity, complete browser-driver correctness or a new live interaction run. Texture registration/physical pixel mapping belongs to the producer review. Reusing an unkeyed viewport across different surfaces is outside the two current parent call paths; those parents explicitly key by surface ID.
